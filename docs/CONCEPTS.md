# Concepts guide

A short course on every idea this repo uses, with a pointer to the file where
you can see it in code. Read in order; later sections build on earlier ones.

## 1. SUMO: the traffic simulator

SUMO (Simulation of Urban MObility) is an open-source *microscopic* simulator:
it moves every vehicle individually (position, speed, acceleration). That is
what you need to test a signal controller, because queues and waiting times
are per-vehicle effects.

A SUMO scenario is a set of XML files:

| File | Contains | Example |
|---|---|---|
| `.nod.xml` | junctions (x, y, type) | `networks/single/single.nod.xml` |
| `.edg.xml` | one-way roads with lane count and speed | `networks/single/single.edg.xml` |
| `.net.xml` | the compiled network, generated by `netconvert` | `networks/single/single.net.xml` |
| `.rou.xml` | demand: vehicle types and flows | `networks/single/RL.rou.xml` |
| `.add.xml` | extras: detectors, signal programs | `networks/single/det.add.xml` |
| `.sumocfg` | ties the files together | `networks/single/RL.sumocfg` |

**Random arrivals.** A flow with `vehsPerHour` releases cars at perfectly even
intervals, so every seed gives the same traffic. We use `probability` instead
(a chance of a new car every second), which gives Poisson-like arrivals, and
different seeds give genuinely different traffic. Without this, "held-out
seeds" would not mean anything.

## 2. Traffic signals

A signal runs a **program**: a list of **phases**, each with a duration and a
state string such as `GGGGrrrr` (one letter per movement: `G` green, `y`
yellow, `r` red). Our junctions have four phases: EB green, EB yellow, SB
green, SB yellow.

Three kinds of control appear in this repo:

- **Fixed-time**: the cycle runs on a timer (42 s green, 3 s yellow), whatever the traffic.
- **Actuated**: a green is extended while cars keep arriving and ends when the gap between cars gets too long. This is what many real cities use. See `networks/*/actuated.add.xml`.
- **RL agents**: learn when to switch from what the detectors see.

Every controller must respect **minimum green** (10 s here, drivers need time
to react) and **yellow clearance** (never jump from green straight to the
conflicting green). `traffic_rl/env.py` enforces both for the agents.

**Lesson learned:** never hardcode which phase serves which road.
`netconvert` decides the order. `TrafficEnv._map_green_phases()` reads it from
the signal program itself.

## 3. TraCI: the control loop

TraCI is SUMO's live API. Python starts SUMO and exchanges commands every step:

```python
traci.start(['sumo', '-c', 'RL.sumocfg'])
while not done:
    count = traci.lanearea.getLastStepVehicleNumber(det)   # 1. read
    action = agent.act(count)                               # 2. decide
    traci.trafficlight.setPhase(tls, next_phase)            # 3. write
    traci.simulationStep()                                  # 4. advance 1 s
traci.close()
```

Every call is a socket round trip, so the environment reads each detector once
per step and shares the result.

## 4. Detectors: how the state is sensed

A **lane-area (E2) detector** is a virtual camera zone on a lane. It reports
how many vehicles are inside it and how many are stopped. Ours cover the last
105 m of every approach lane and end at the stop line. In the field, the same
numbers would come from a camera and a vision model; the agent does not care
where the count comes from.

The SEMMA study ([SEMMA.md](SEMMA.md)) found that the original detectors ended
10 to 16 m before the stop line and missed the first cars in every queue.
Always check that your sensors see what you think they see.

## 5. Reinforcement learning

An **agent** sees a **state** s, picks an **action** a, and the environment
returns a **reward** r and the next state s'. The goal is to maximize the
discounted sum of rewards, not just the next one. Formally this is a
**Markov Decision Process** (MDP).

| RL term | Here | Code |
|---|---|---|
| Agent | one traffic light | `traffic_rl/q_learning.py`, `dqn.py` |
| State | detector counts, which road has green, how long it has been green | `traffic_rl/state.py` |
| Action | 0 keep the green, 1 switch | `traffic_rl/env.py` |
| Reward | minus the mean queue since the last decision | `traffic_rl/baselines.py: queue_reward` |
| Discount gamma | 0.9 per decision | agents |

**When the agent decides.** It is only asked when a switch is allowed (after
the minimum green), then every 5 s while it keeps. A switch is followed by 3 s
of yellow and 10 s of minimum green before the next question. So every action
has a real, visible effect. The first version of this project decided every
0.1 s, where one "switch" barely changes anything, and the DQN could not tell
the actions apart (see "What did not work" in the README).

## 6. Q-learning

Learn a table Q(s, a) = the expected future reward of taking a in s and acting
well afterwards. Then the policy is simply argmax_a Q(s, a).

```
Q(s,a) <- Q(s,a) + alpha * [ r + gamma * max_a' Q(s',a') - Q(s,a) ]
                             \_____ TD target _____/
```

- **alpha** (0.1): how far to move toward the new evidence
- **gamma** (0.9): how much the future counts
- **off-policy**: it learns the value of the greedy policy even while exploring
- **model-free**: it needs no model of traffic dynamics

**Exploration.** With probability epsilon the agent acts randomly. Epsilon
starts at 1.0 and decays to 0.05 over the first 60% of training.

**Binning.** Raw counts give too many states, so counts are binned at edges
chosen from the data (2, 4, 7, 11 vehicles). The number of table rows is a
direct measure of how much of the world the agent has seen; the training logs
record it every episode.

## 7. Deep Q-Network (DQN)

A table cannot generalize: learning about (5 cars, 3 cars) teaches it nothing
about (5 cars, 4 cars). A DQN replaces the table with a neural network
Q(s; theta), so similar states share what was learned, and it can take all six
lane counts as input.

Naive DQN is unstable. Three standard fixes are in `traffic_rl/dqn.py`:

- **Experience replay** (Lin 1992, Mnih et al. 2015): store transitions and
  train on random mini-batches, so consecutive, highly similar samples do not
  dominate an update.
- **Target network**: compute the TD target with a frozen copy of the network,
  synced every 250 updates, so the target does not move with every step.
- **Double DQN target** (van Hasselt et al. 2016): the online network picks the
  best next action and the target network scores it. This reduces the
  overestimation that plain max-based targets cause.

Plus **Huber loss** (quadratic for small errors, linear for big ones) so one
surprising transition cannot blow up the weights. The network, backprop and
Adam are about 50 lines of NumPy, and a unit test checks the gradients against
finite differences.

## 8. Multi-agent RL

Optimizing one junction can just push congestion to the next one. A corridor
needs junctions that cooperate.

- **Distributed, not centralized**: one small agent per junction. A single agent
  controlling everything would face a joint action space that grows
  exponentially with the number of junctions.
- **Independent learners** (Tan 1993): each agent sees only its own detectors.
  Simple, but each agent treats its neighbor as unpredictable noise.
- **Coordinated learners** (this project): neighbors exchange a small message
  (which road has green, how many cars they see). The message joins the state,
  and half of the neighbor's queue joins the reward, so an agent "feels" the
  congestion it sends downstream. See `traffic_rl/multi_agent.py`.
- **Non-stationarity**: each agent's world includes another agent that is also
  learning, so the environment keeps changing. Single-agent convergence
  guarantees no longer hold. Small state spaces, a slow learning rate and
  epsilon decay keep it workable here.

## 9. Evaluation

- **Held-out seeds**: training uses seeds 0-199, validation 500-502, evaluation
  1000-1009. A result on traffic the agent trained on proves nothing.
- **Paired comparison**: every controller sees the same 10 seeds, so the
  difference per seed removes most traffic-to-traffic noise.
- **Bootstrap confidence intervals** (Efron and Tibshirani 1993): resample the
  10 per-seed results 10,000 times to get a 95% interval without assuming a
  normal distribution.
- **Before vs after**: the same agent with its initial parameters versus after
  training. This isolates what learning added.
- **Metrics the agent did not optimize**: it is trained on queue length, but we
  also report waiting time and travel time. If those improve too, the reward is
  a good proxy.
- **Q-value probes**: hand-made states with an obvious right answer (busy road
  on red, empty road on green: switch). They check the agent learned traffic
  logic and not just numbers.

## 10. Glossary

| Term | Meaning |
|---|---|
| Edge, lane, link | road segment, its lanes, one movement through a junction |
| Phase, program | one signal state with a duration, the cycle of phases |
| E2 detector | virtual camera zone that counts vehicles |
| TraCI | SUMO's live control API |
| MDP | decision model where the next state depends only on the current state and action |
| Policy | the agent's rule from state to action |
| TD target | r + gamma * max Q(s', .), the estimate that learning moves toward |
| Epsilon-greedy | act randomly with probability epsilon, else greedily |
| Experience replay | memory of past transitions, sampled in random mini-batches |
| Target network | frozen copy of the network used for TD targets |
| Reward shaping | extra reward terms that steer behavior (the neighbor share) |
| Non-stationarity | the environment changes because other agents are learning |
| Minimum green | shortest allowed green time |
